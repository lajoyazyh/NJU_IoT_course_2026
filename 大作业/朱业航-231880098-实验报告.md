## 一、项目概述

本项目实现了一个面向课堂场景的多人人脸检测与表情识别系统。系统可以接收图片、视频和摄像头画面作为输入，自动检测画面中的多人脸区域，对每张人脸进行表情识别，然后统计整体表情分布，并根据表情比例判断课堂整体状态。

系统的核心目标不是只完成单张图片上的表情分类，而是围绕“课堂状态分析”构建一个完整应用：包括多人脸检测、表情识别、课堂状态判断、视频时序分析、结果可视化、历史记录保存和结果包导出。为了方便课程演示和助教提问，本项目还对原始实现进行了模块化重构，将算法流程、时序分析和界面展示分离到不同模块中。

系统支持的输入方式包括：

- 图片上传：上传包含多个人脸的图片，输出标注结果和统计信息。
- 视频上传：按时间间隔采样视频帧，输出时序趋势、预警结果和关键采样帧。
- 摄像头拍照：通过浏览器拍照后进行单帧分析。
- 本地实时摄像头：通过 OpenCV 直接读取本机摄像头，适合课堂演示。
- WebRTC 实时流：保留为实验性入口，用于浏览器实时视频流分析。

## 四、系统总体设计

### 4.1 总体流程

系统整体流程如下：

```text
图片 / 视频 / 摄像头输入
        ↓
输入层将数据转换为 BGR 图像帧
        ↓
pipeline.py 统一单帧分析
        ↓
face_detector.py 检测人脸位置
        ↓
expression_recognizer.py 识别人脸表情
        ↓
analyzer.py 统计表情分布并判断课堂状态
        ↓
utils.py 绘制标注图、保存 CSV、导出结果包
        ↓
app.py 使用 Streamlit 展示结果
```

如果输入是视频，则会增加一层时序分析：

```text
视频文件
        ↓
temporal_analyzer.py 按秒采样视频帧
        ↓
每个采样帧调用 pipeline.analyze_frame()
        ↓
生成逐帧记录 frame_records
        ↓
计算平均每帧人数、表情趋势、关键帧、三级预警和性能指标
```

### 4.2 模块划分

| 模块 | 文件 | 主要职责 |
|---|---|---|
| 界面调度层 | `app.py` | Streamlit 页面、输入选择、参数设置、结果展示 |
| 人脸检测层 | `face_detector.py` | 检测图片中的多个人脸 |
| 表情识别层 | `expression_recognizer.py` | 加载 CNN3 模型并识别 7 类表情 |
| 统计规则层 | `analyzer.py` | 计算表情比例、判断课堂状态、视频预警 |
| 单帧管线层 | `pipeline.py` | 统一图片、视频帧、摄像头帧的处理流程 |
| 视频时序层 | `temporal_analyzer.py` | 视频采样、逐帧日志、趋势分析和预警 |
| 工具函数层 | `utils.py` | 中文标注、CSV 读写、结果图和结果包导出 |

这样的设计使系统逻辑更加清楚。图片、视频和摄像头虽然输入形式不同，但进入算法后都被统一看作一帧图像，因此都可以复用同一个 `pipeline.py`。

## 五、人脸检测模块设计

### 5.1 设计目标

课堂场景中的人脸检测具有以下难点：

- 人数较多，同一张图片中可能出现多个学生。
- 人脸尺度差异较大，前排和后排人脸大小不同。
- 可能存在低头、侧脸、模糊、遮挡等情况。
- 单一检测器容易出现漏检或误检。

因此，本项目没有只依赖一个检测器，而是采用 MediaPipe 与 Haar Cascade 双检测器结合的方式。

### 5.2 MediaPipe 检测

MediaPipe Face Detection 是一个轻量级人脸检测方案，适合实时应用。本项目使用它作为主要检测器，优点是速度快、精度较高、对常见正脸场景比较稳定。

核心步骤：

1. 将 OpenCV 的 BGR 图像转换为 RGB。
2. 调用 MediaPipe Face Detection。
3. 将归一化边界框转换为图像像素坐标。
4. 输出格式为 `(x1, y1, x2, y2, confidence)`。

### 5.3 Haar Cascade 检测

OpenCV Haar Cascade 是传统人脸检测方法。本项目将它作为补充检测器，主要用于提高召回率。虽然 Haar Cascade 的精度不如深度学习检测器，但在某些场景下可以补充 MediaPipe 漏掉的人脸。

核心参数包括：

| 参数 | 作用 |
|---|---|
| `scaleFactor=1.1` | 多尺度检测时图像缩放比例 |
| `minNeighbors=3` | 候选框保留条件 |
| `minSize` | 最小人脸尺寸 |

### 5.4 双检测器合并与 NMS 去重

如果直接把两个检测器的结果简单相加，同一个人脸可能会被重复统计。因此系统使用 NMS，即非极大值抑制，对重复框进行去重。

处理流程：

```text
MediaPipe 检测结果
        +
Haar Cascade 检测结果
        ↓
按置信度排序
        ↓
计算检测框 IoU
        ↓
IoU > 0.4 的框视为重复框
        ↓
保留置信度更高的框
```

这种设计提高了多人场景下的召回率，同时避免重复框导致人数统计错误。

## 六、表情识别模块设计

### 6.1 模型来源

表情识别模块复用了实验二中训练得到的 CNN3 模型，模型权重文件为：

```text
ClassroomStateAnalyzer/models/cnn3_best_weights.h5
```

模型输入为 `48×48×1` 的灰度人脸图像，输出 7 类表情的概率分布。

7 类表情包括：

| 英文标签 | 中文含义 |
|---|---|
| Angry | 生气 |
| Disgust | 厌恶 |
| Fear | 恐惧 |
| Happy | 开心 |
| Sad | 悲伤 |
| Surprise | 惊讶 |
| Neutral | 中性 |

### 6.2 人脸预处理

识别前需要先对检测到的人脸区域进行预处理：

1. 根据人脸框从原图中裁剪人脸。
2. 转换为灰度图。
3. resize 到 `48×48`。
4. 像素值归一化到 `[0, 1]`。
5. 增加 batch 维度，送入 CNN3 模型。

### 6.3 普通模式与快速模式

项目中提供两种识别策略：

| 模式 | 方法 | 适用场景 |
|---|---|---|
| 普通模式 | 对每个人脸生成多个增强版本，再取平均结果 | 图片分析，追求稳定性 |
| 快速模式 | 多个人脸组成 batch，一次模型推理 | 视频和摄像头实时分析 |

快速模式的意义在于降低延迟。视频和实时摄像头需要连续处理多帧，如果每个人脸都进行多次增强推理，会明显降低响应速度。因此系统默认在实时场景中启用快速模式。

### 6.4 模型单例与预热

为了避免每次分析都重新加载模型，系统使用单例模式管理表情识别器：

```python
recognizer = get_recognizer()
recognizer.warm_up()
```

`warm_up()` 会在系统启动时执行一次空预测，减少 TensorFlow 第一次推理时的冷启动延迟。

## 七、统一单帧分析管线设计

### 7.1 设计原因

图片、视频和摄像头本质上都可以转化为图像帧。如果每一种输入模式都单独写一套检测、识别、统计和绘图逻辑，容易产生以下问题：

- 参数不一致，例如图片模式和视频模式使用不同置信度阈值。
- 代码重复，后续修改成本高。
- 演示时不容易解释系统结构。

因此系统新增 `pipeline.py`，将单帧分析过程统一封装为：

```python
analyze_frame(frame_bgr, recognizer, config)
```

### 7.2 AnalysisConfig

`AnalysisConfig` 用于集中管理核心分析参数：

| 参数 | 含义 |
|---|---|
| `fast_mode` | 是否启用快速识别模式 |
| `confidence_threshold` | 表情识别置信度阈值 |
| `detection_sensitivity` | 人脸检测灵敏度 |
| `merge_detectors` | 是否启用双检测器合并 |

### 7.3 单帧处理步骤

`analyze_frame()` 的内部流程为：

1. 调用 `detect_faces()` 检测人脸框。
2. 调用表情识别器识别每个人脸的表情。
3. 根据置信度阈值过滤低置信度结果。
4. 调用 `calculate_statistics()` 统计表情分布。
5. 调用 `judge_classroom_state()` 判断课堂状态。
6. 调用 `draw_results()` 绘制人脸框和中文表情标签。
7. 返回分析结果和耗时。

返回结果包括：

| 字段 | 说明 |
|---|---|
| `faces` | 检测到的人脸框 |
| `raw_recognition_results` | 过滤前的识别结果 |
| `recognition_results` | 过滤后的识别结果 |
| `stats` | 表情统计信息 |
| `state_text` | 课堂状态文字 |
| `state_level` | 课堂状态等级 |
| `result_image` | 标注后图像 |
| `elapsed_ms` | 单帧分析耗时 |

## 八、统计分析与课堂状态判断

### 8.1 表情统计

`analyzer.py` 中的 `calculate_statistics()` 会对所有识别结果进行汇总，输出：

- 检测人数。
- 每种表情的人数。
- 每种表情的比例。
- 当前主要表情。

例如，如果检测到 5 个人，其中 3 个为 Neutral，2 个为 Sad，则统计结果中 `Neutral_ratio=0.6`，`Sad_ratio=0.4`。

### 8.2 课堂状态规则

课堂状态判断采用可解释的规则方法。规则如下：

| 优先级 | 判断条件 | 课堂状态 |
|---|---|---|
| 1 | 检测人数为 0 | 未检测到学生 |
| 2 | Happy + Neutral 占比 ≥ 70% | 课堂状态良好 |
| 3 | Sad + Angry 占比 ≥ 40% | 课堂状态较低落，需要关注 |
| 4 | Neutral 是主要表情 | 课堂状态平稳 |
| 5 | Surprise 占比 ≥ 30% | 课堂注意力波动较大 |
| 6 | 其他情况 | 课堂状态一般 |

使用规则判断的优点是逻辑清晰、可解释性强，适合课程项目演示。助教或教师可以直接根据表情比例理解系统为什么给出某种课堂状态。

### 8.3 视频预警规则

为了让视频分析不仅是单帧统计的简单叠加，系统增加了视频时序预警：

| 预警等级 | 触发条件 |
|---|---|
| 绿色状态 | 连续 10 个采样帧课堂状态良好 |
| 黄色预警 | 连续 5 个采样帧中性比例偏高 |
| 红色预警 | 连续 3 个采样帧处于低落或注意力波动状态 |

预警结果会在视频分析报告中展示，并保存到 `video_summary.json` 中。

## 九、视频时序分析模块设计

### 9.1 设计动机

视频和图片最大的区别在于视频具有时间维度。如果只把视频中的所有采样帧识别结果合并后统计，就会出现一个问题：同一个学生在不同帧中会被重复统计为多个人。

因此，系统对视频统计口径进行了重新设计：

- 不把跨帧累计人脸数称为“检测人数”。
- 使用“人脸实例数”表示所有采样帧中的累计人脸出现次数。
- 使用“平均每帧人数”表示课堂画面中的平均人数。
- 使用“峰值人数”表示某个采样帧中最多检测到的人数。
- 表情比例使用每个采样帧比例的平均值，而不是简单累计所有人脸后计算。

### 9.2 视频分析流程

`temporal_analyzer.py` 的主要函数为：

```python
analyze_video(video_path, recognizer, config, sample_every_seconds, max_frames)
```

处理流程：

```text
打开视频文件
        ↓
读取 FPS 和总帧数
        ↓
根据 sample_every_seconds 计算采样间隔
        ↓
逐帧读取视频
        ↓
到达采样帧时调用 analyze_frame()
        ↓
生成 frame_records
        ↓
计算视频摘要、关键帧、预警和性能指标
```

### 9.3 frame_records 字段

视频逐帧日志中每条记录包括：

| 字段 | 含义 |
|---|---|
| `sample_index` | 第几个采样帧 |
| `frame_index` | 原视频帧号 |
| `time_sec` | 视频时间点 |
| `total_count` | 当前采样帧检测人数 |
| `main_expression` | 当前采样帧主要表情 |
| `state_text` | 当前采样帧课堂状态 |
| `elapsed_ms` | 当前采样帧分析耗时 |
| `Happy_ratio` 等 | 各表情在当前帧中的比例 |

## 十三、遇到的问题与优化

### 13.1 WebRTC 实时流连接问题

在浏览器实时流模式中，曾出现：

```text
Connection is taking longer than expected
```

该问题与 WebRTC 的 ICE/STUN 协商、浏览器权限和网络环境有关。为提高演示稳定性，系统增加了 OpenCV 本地实时摄像头模式，不依赖浏览器 WebRTC 协商，适合本机课堂演示。

### 13.2 视频统计口径问题

原始视频统计容易把同一个人在不同采样帧中的出现累计为多个人。为解决该问题，系统将视频统计改为：

- 人脸实例数：跨帧累计的人脸出现次数。
- 平均每帧人数：更适合表示视频中的课堂规模。
- 峰值人数：单帧最大检测人数。
- 按帧平均表情比例：避免长视频或多人帧对结果产生不合理影响。

### 13.3 保存结果逻辑问题

原本“保存结果图片”的逻辑只适合图片，不适合视频。现在系统改为“保存当前结果包”：

- 图片和摄像头保存标注图、摘要和人脸明细。
- 视频保存摘要、时序 CSV 和关键帧。

这样提交代码时，`results` 文件夹中能够完整反映系统运行结果。

### 13.4 模块化优化

原先部分逻辑集中在 `app.py` 中，不利于讲解和维护。优化后：

- `app.py` 只负责界面。
- `pipeline.py` 负责单帧处理。
- `temporal_analyzer.py` 负责视频时序。
- `analyzer.py` 负责统计规则。
- `utils.py` 负责保存和导出。

这种结构更符合软件工程中的分层设计思想。

## 十四、创新点与特色实现

本项目的特色实现包括：

1. **双检测器合并**：MediaPipe 与 Haar Cascade 并行检测，再通过 NMS 去重，提高多人场景下召回率。
2. **统一单帧 pipeline**：图片、视频帧和摄像头帧共享同一分析流程，减少重复代码。
3. **视频时序分析**：不是简单统计所有帧，而是输出逐帧日志、趋势变化和三级预警。
4. **视频统计口径优化**：区分人脸实例数、平均每帧人数和峰值人数。
5. **本地实时摄像头模式**：解决 WebRTC 在本机演示中不稳定的问题。
6. **按模态导出结果包**：图片/摄像头和视频分别保存不同结构的运行结果。
7. **中文可视化标注**：通过 PIL 绘制中文表情标签，解决 OpenCV 中文显示问题。

## 十五、局限性与改进方向

虽然系统已经完成主要功能，但仍有一些局限：

| 局限性 | 改进方向 |
|---|---|
| 表情识别模型基于 FER2013，真实课堂适应性有限 | 使用更大规模数据集或课堂场景数据微调模型 |
| 视频未做跨帧身份跟踪 | 引入目标跟踪或人脸 ReID，统计唯一学生人数 |
| 课堂状态规则较简单 | 引入机器学习模型或多模态特征进行状态判断 |
| WebRTC 受浏览器和网络影响 | 演示时优先使用本地实时模式，部署时配置 HTTPS/TURN |
| 人脸遮挡和侧脸仍可能漏检 | 引入更强的人脸检测模型，如 RetinaFace 或 YOLO-face |

## 十六、总结

本项目完成了一个完整的课堂状态分析系统，能够对图片、视频和摄像头画面进行多人人脸检测与表情识别，并根据表情分布判断课堂状态。系统不仅完成了基础识别功能，还增加了视频时序分析、三级预警、本地实时摄像头、结果包导出等功能。

从软件结构上看，项目采用模块化设计，将人脸检测、表情识别、统计规则、单帧管线、视频时序和界面展示分离，使代码结构更加清晰，也便于向助教说明每个部分的实现位置和方法。

从运行结果看，系统已经生成了图片/摄像头结果包、视频结果包和历史记录 CSV，`results` 文件夹可以直接作为实验代码提交时的运行结果证明。整体上，本项目满足期末大作业对实验报告、代码和运行结果的提交要求。
