# 课堂状态分析系统架构说明

> 本文用于解释项目的整体架构、模块职责、核心数据流和关键代码原理。  
> 适合现场答辩、助教追问实现细节、或后续维护代码时参考。

---

## 一、系统要解决的问题

本项目要完成的是一个“基于多人人脸检测与表情识别的课堂状态分析系统”。它不是只识别一张单人表情图，而是要处理课堂这种多人场景：

1. 输入可能是图片、视频或摄像头画面。
2. 画面中可能有多个人脸。
3. 系统需要先找出所有人脸位置。
4. 再对每个人脸分别识别表情。
5. 最后统计全班表情分布，并判断课堂状态。

因此系统不是单一模型直接输出结果，而是由多个模块串联完成：

```text
输入图像/视频/摄像头
→ 人脸检测
→ 人脸裁剪
→ 表情识别
→ 多人统计
→ 课堂状态判断
→ 可视化展示
→ CSV/图片/时序日志保存
```

---

## 二、总体架构

项目采用“输入层 + 单帧分析管线 + 时序分析 + 展示导出”的结构。

```text
app.py
  负责 Streamlit 界面、用户输入、结果展示

pipeline.py
  负责统一处理一帧图像

face_detector.py
  负责检测人脸位置

expression_recognizer.py
  负责识别人脸表情

analyzer.py
  负责统计表情分布、判断课堂状态、计算视频预警

temporal_analyzer.py
  负责视频采样、逐帧时序分析、性能统计

utils.py
  负责中文标注、图片保存、CSV 保存与导出
```

可以向助教这样概括：

> 图片、视频和摄像头只是输入来源不同。进入算法后，它们都会先变成一帧 BGR 图像，再交给 `pipeline.py` 做统一单帧分析。视频只是多次调用单帧分析，并在 `temporal_analyzer.py` 中形成时间序列和预警。

## 四、核心设计思想：一切先统一成“单帧分析”

图片、视频和摄像头看起来是三种功能，但底层处理逻辑高度相同。

| 输入方式 | 实际处理方式 |
|----------|--------------|
| 图片上传 | 直接分析这一张图 |
| 视频上传 | 从视频中按时间间隔抽取多张图 |
| 摄像头拍照 | 拍一张图后分析 |
| 本地实时摄像头 | 连续读取摄像头帧，隔几帧分析一次 |
| WebRTC 实时流 | 浏览器传来每帧图像后分析 |

所以系统抽象出一个统一函数：

```python
analysis = analyze_frame(frame_bgr, recognizer, config)
```

这就是 `pipeline.py` 的核心。它把所有输入模式共享的步骤集中起来，避免图片、视频、摄像头各写一套重复逻辑。

这样做的好处：

1. 参数一致：置信度阈值、检测灵敏度、快速模式都统一生效。
2. 结果一致：图片、视频帧、摄像头帧的统计规则完全相同。
3. 便于讲解：输入层只负责提供图像帧，pipeline 负责算法处理。
4. 便于扩展：以后增加批量图片、网络摄像头，也只要把输入变成帧即可。

## 五、`pipeline.py`：单帧分析管线

### 5.1 模块职责

`pipeline.py` 是项目的核心组织模块，它把一帧图像从输入到结果的完整流程封装起来。

核心接口：

```python
AnalysisConfig
analyze_frame(frame_bgr, recognizer, config)
```

### 5.2 `AnalysisConfig`

`AnalysisConfig` 是一个参数配置对象：

```python
@dataclass
class AnalysisConfig:
    fast_mode: bool = True
    confidence_threshold: float = 0.3
    detection_sensitivity: float = 0.3
    merge_detectors: bool = True
```

各字段含义：

| 字段 | 作用 |
|------|------|
| `fast_mode` | 是否使用快速批量识别 |
| `confidence_threshold` | 表情识别置信度阈值 |
| `detection_sensitivity` | MediaPipe 人脸检测灵敏度 |
| `merge_detectors` | 是否合并 MediaPipe 和 Haar 检测结果 |

这些参数来自 Streamlit 侧边栏，因此用户在界面中修改参数后，图片、视频、摄像头都会同步使用同样配置。

### 5.3 `analyze_frame()` 工作流程

```text
输入 frame_bgr
→ detect_faces()
→ recognizer.recognize_all_fast() 或 recognize_all()
→ filter_recognition_results()
→ calculate_statistics()
→ judge_classroom_state()
→ draw_results()
→ 返回 analysis 字典
```

返回结果包含：

| 字段 | 含义 |
|------|------|
| `faces` | 原始检测到的人脸框 |
| `raw_recognition_results` | 过滤前识别结果 |
| `recognition_results` | 置信度过滤后的识别结果 |
| `stats` | 表情统计结果 |
| `state_text` | 中文课堂状态 |
| `state_level` | 状态等级 |
| `result_image` | 标注后图像 |
| `elapsed_ms` | 单帧处理耗时 |

### 5.4 置信度过滤

之前界面里有“置信度阈值”，但不一定所有路径都真正使用。现在统一放进 pipeline：

```python
recognition_results = filter_recognition_results(
    raw_results,
    config.confidence_threshold,
)
```

这表示：

- 模型仍然会对检测到的人脸做识别；
- 但低于阈值的识别结果不会参与统计；
- 课堂状态判断也只基于过滤后的结果。

这样可以减少低置信度识别对课堂状态的干扰。

## 六、`face_detector.py`：人脸检测模块

### 6.1 模块职责

`face_detector.py` 负责回答一个问题：

> 画面中哪里有人脸？

它不负责识别表情，只返回人脸位置。

输出格式：

```python
[(x1, y1, x2, y2, confidence), ...]
```

每个元组表示一个人脸框：

- `x1, y1`：左上角坐标
- `x2, y2`：右下角坐标
- `confidence`：检测置信度

### 6.2 双检测器策略

系统使用两个检测器：

1. **MediaPipe Face Detection**
   - 速度快
   - 适合正脸和较远距离人脸
   - 输出检测置信度

2. **OpenCV Haar Cascade**
   - 传统方法
   - 对部分正脸/轻微倾斜场景有补充作用
   - 不输出真实置信度，代码中统一给默认值 `0.8`

主函数：

```python
detect_faces(
    image_bgr,
    use_mediapipe=True,
    merge_detectors=True,
    min_conf_mediapipe=0.3,
)
```

### 6.3 为什么要合并检测器

课堂图像通常有多人、远近不同、姿态不同的问题。单个检测器容易漏检。

系统默认启用：

```text
MediaPipe 检测结果
+ Haar 检测结果
→ NMS 去重
→ 最终人脸框
```

### 6.4 NMS 去重

两个检测器可能检测到同一张脸，因此需要去重。代码中使用 IoU 判断重叠程度：

```python
compute_iou(box1, box2)
```

如果两个框的 IoU 大于阈值 `0.4`，就认为是重复框，只保留置信度更高的一个。

## 七、`expression_recognizer.py`：表情识别模块

### 7.1 模块职责

`expression_recognizer.py` 负责回答：

> 每张人脸是什么表情？

它接收：

- 原始图像
- 人脸框列表

然后对每个人脸进行裁剪、预处理和模型预测。

### 7.2 模型结构

系统使用 CNN3 模型，输入尺寸为：

```text
48 × 48 × 1
```

也就是灰度人脸图像。

输出为 7 类表情：

| 英文 | 中文 |
|------|------|
| Angry | 生气 |
| Disgust | 厌恶 |
| Fear | 恐惧 |
| Happy | 开心 |
| Sad | 悲伤 |
| Surprise | 惊讶 |
| Neutral | 中性 |

### 7.3 预处理流程

对每个人脸：

```text
根据人脸框裁剪
→ 转灰度
→ 归一化到 [0, 1]
→ resize 到 48×48
→ 添加 channel 维度
→ 输入 CNN3 模型
```

### 7.4 普通模式和快速模式

系统提供两种识别模式：

| 模式 | 函数 | 特点 |
|------|------|------|
| 普通模式 | `recognize_all()` | 每张脸使用多种增广变体，准确性略高 |
| 快速模式 | `recognize_all_fast()` | 所有人脸组成 batch，一次预测，速度更快 |

现场演示建议开启快速模式，因为课堂项目更看重响应速度。

### 7.5 单例和预热

模型加载较慢，所以系统使用全局单例：

```python
get_recognizer()
```

第一次进入应用时加载模型，并调用：

```python
warm_up()
```

这样可以减少 TensorFlow 首次推理的冷启动延迟。

## 八、`analyzer.py`：统计、课堂状态和预警规则

### 8.1 表情统计

`calculate_statistics()` 接收识别结果列表，统计：

- 总人数
- 各表情人数
- 各表情比例
- 主要表情
- 主要表情中文名

核心思路：

```python
total_count = len(recognition_results)
expression_count[label_en] += 1
expression_ratio = count / total_count
main_expression = count 最大的类别
```

### 8.2 课堂状态判断

`judge_classroom_state()` 使用规则判断课堂状态。

规则顺序：

| 优先级 | 条件 | 状态 |
|--------|------|------|
| 1 | 检测人数为 0 | 未检测到学生 |
| 2 | Happy + Neutral ≥ 70% | 课堂状态良好 |
| 3 | Sad + Angry ≥ 40% | 课堂状态较低落，需要关注 |
| 4 | Neutral 是主要表情 | 课堂状态平稳 |
| 5 | Surprise ≥ 30% | 注意力波动较大 |
| 6 | 其他情况 | 课堂状态一般 |

这里使用规则系统而不是再训练一个课堂状态模型，原因是：

1. 作业要求只需要简单状态判断；
2. 规则透明，便于解释；
3. 数据量不足时，规则比额外模型更稳定。

### 8.3 视频三级预警

`calculate_temporal_warning()` 用于视频时序分析。

它接收逐帧记录 `frame_records`，根据连续帧状态判断预警：

| 预警 | 条件 |
|------|------|
| 红色预警 | 连续 3 个采样帧为低落或注意力波动 |
| 黄色预警 | 连续 5 个采样帧平稳且 Neutral 平均占比 ≥ 65% |
| 绿色状态 | 连续 10 个采样帧状态良好 |
| 正常 | 未触发上述条件 |

红色预警优先级最高，因此一旦出现连续低落/注意力波动，就立即返回红色预警。

## 九、`temporal_analyzer.py`：视频时序分析模块

### 9.1 为什么需要这个模块

普通视频分析只回答：

> 这段视频整体表情分布是什么？

但延展任务要求回答：

> 课堂状态随时间如何变化？有没有连续低落、注意力下滑或状态突变？

因此系统新增 `temporal_analyzer.py`，专门处理视频时序。

### 9.2 视频分析流程

核心函数：

```python
analyze_video(
    video_path,
    recognizer,
    config,
    sample_every_seconds=1.0,
    max_frames=60,
    progress_callback=None,
)
```

流程：

```text
cv2.VideoCapture 打开视频
→ 获取 FPS 和总帧数
→ 根据 sample_every_seconds 计算采样间隔
→ 每到采样帧，调用 pipeline.analyze_frame()
→ 生成一条 frame_record
→ 汇总所有 recognition_results
→ 计算整体统计
→ 计算三级预警
→ 计算性能指标
→ 返回结果
```

### 9.3 采样策略

默认：

```python
sample_every_seconds = 1.0
```

也就是约 1 秒 1 帧。

代码中根据 FPS 计算真实帧间隔：

```python
frame_interval = round(fps * sample_every_seconds)
```

例如：

- 视频 30 FPS，1 秒采样一次，则每 30 帧分析一次；
- 视频 25 FPS，1 秒采样一次，则每 25 帧分析一次。

这样比固定“每 30 帧”更通用。

### 9.4 逐帧记录

每个采样帧生成一条记录：

| 字段 | 含义 |
|------|------|
| `sample_index` | 第几个采样帧 |
| `frame_index` | 原视频帧号 |
| `time_sec` | 视频时间秒 |
| `total_count` | 当前帧检测并纳入统计的人脸数 |
| `main_expression` | 当前帧主要表情 |
| `state_text` | 当前帧课堂状态 |
| `state_level` | 当前帧状态等级 |
| `elapsed_ms` | 当前帧分析耗时 |
| `Happy_ratio` 等 | 各表情比例 |

这些记录会用于：

1. 时序折线图；
2. 三级预警判断；
3. 导出 `results/temporal_*.csv`；
4. 现场说明系统运行速度。

### 9.5 性能指标

`analyze_video()` 返回：

```python
performance = {
    "total_video_frames": ...,
    "fps": ...,
    "sample_interval_frames": ...,
    "sample_every_seconds": ...,
    "analyzed_frames": ...,
    "face_instances": ...,
    "total_elapsed_sec": ...,
    "avg_elapsed_ms_per_frame": ...,
}
```

这些指标对应说明书中的“对系统运行速度进行测试”加分项。

## 十、`utils.py`：可视化与导出模块

### 10.1 中文绘制

OpenCV 默认不擅长绘制中文，所以系统使用 PIL 中转：

```text
OpenCV BGR
→ PIL RGB
→ ImageDraw 绘制中文
→ 转回 OpenCV BGR
```

核心函数：

```python
cv2_img_add_text()
```

字体文件：

```text
assets/simsun.ttc
```

### 10.2 绘制识别结果

`draw_results()` 会在图像上绘制：

- 人脸框
- 中文表情标签
- 表情置信度

不同表情使用不同颜色，方便观察。

### 10.3 数据保存

`utils.py` 负责三类保存：

| 函数 | 作用 |
|------|------|
| `save_record()` | 保存一次总体检测记录到 `records.csv` |
| `save_result_image()` | 保存标注后的检测结果图片 |
| `export_csv()` | 导出历史记录 |
| `export_temporal_csv()` | 导出视频逐帧时序日志 |

其中：

- `records.csv` 保存每次分析的总体结果；
- `temporal_*.csv` 保存视频每个采样帧的详细时序结果。

两者分开保存，可以避免常规历史记录表字段过多、难以阅读。

## 十一、`app.py`：Streamlit 界面调度层

### 11.1 模块职责

`app.py` 不再承担主要算法逻辑，而是负责：

1. 页面布局；
2. 侧边栏参数；
3. 文件上传；
4. 摄像头输入；
5. 调用 `pipeline.py` 和 `temporal_analyzer.py`；
6. 展示图片、图表、表格和状态；
7. 保存记录。

### 11.2 Session State

Streamlit 页面每次交互都会重新运行脚本，因此需要用 `st.session_state` 保存当前结果：

| 状态字段 | 作用 |
|----------|------|
| `recognizer` | 模型单例 |
| `current_image` | 当前原始图像 |
| `result_image` | 当前标注结果图 |
| `recognition_results` | 当前识别结果 |
| `stats` | 当前统计结果 |
| `state_text` | 当前课堂状态 |
| `temporal_records` | 视频逐帧记录 |
| `temporal_warning` | 视频预警结果 |
| `video_performance` | 视频性能指标 |
| `temporal_csv_path` | 时序日志导出路径 |

### 11.3 图片模式

图片模式调用：

```python
process_image(image, image_name)
```

内部会：

```text
PIL Image
→ OpenCV BGR
→ analyze_frame()
→ 写入 session_state
→ save_current_record()
```

### 11.4 视频模式

视频模式调用：

```python
result = analyze_video(...)
```

然后把结果写入：

- `recognition_results`
- `stats`
- `state_text`
- `temporal_records`
- `temporal_warning`
- `video_performance`
- `temporal_csv_path`

页面会展示：

- 整体统计；
- 表情分布柱状图；
- 课堂状态；
- 时序折线图；
- 预警信息；
- 逐帧日志；
- 性能指标。

### 11.5 摄像头模式

系统提供三种摄像头入口：

| 模式 | 技术 | 推荐程度 |
|------|------|----------|
| 拍照模式 | `st.camera_input` | 稳定，适合兜底 |
| 本地实时模式 | `cv2.VideoCapture` | 推荐现场演示 |
| WebRTC 模式 | `streamlit-webrtc` | 实验性，受网络环境影响 |

本地实时模式的逻辑：

```text
cv2.VideoCapture(摄像头编号)
→ 循环读取 frame
→ 每隔 N 帧调用 analyze_frame()
→ 展示标注图和当前统计
→ 结束后保存最后一次结果
```

WebRTC 模式虽然保留，但不建议作为唯一演示路线，因为它依赖浏览器权限、HTTPS、本地网络和 STUN/TURN 协商。

## 十二、数据流详解

### 12.1 图片数据流

```text
用户上传图片
→ app.py 读取为 PIL Image
→ 转换为 BGR 图像
→ pipeline.analyze_frame()
→ face_detector.detect_faces()
→ expression_recognizer.recognize_all_fast()
→ analyzer.calculate_statistics()
→ analyzer.judge_classroom_state()
→ utils.draw_results()
→ app.py 展示结果
→ utils.save_record()
```

### 12.2 视频数据流

```text
用户上传视频
→ app.py 保存为临时文件
→ temporal_analyzer.analyze_video()
→ cv2.VideoCapture 读取视频
→ 按秒采样关键帧
→ 每个采样帧调用 pipeline.analyze_frame()
→ 汇总 all recognition_results
→ 生成 frame_records
→ analyzer.calculate_temporal_warning()
→ utils.export_temporal_csv()
→ app.py 展示整体统计、时序图、预警和性能
```

### 12.3 摄像头数据流

```text
本地摄像头
→ cv2.VideoCapture
→ 循环读取 frame
→ 每隔 N 帧调用 pipeline.analyze_frame()
→ 实时展示 result_image
→ 结束后保存最后一次结果
```

## 十三、关键设计取舍

### 13.1 为什么用规则判断课堂状态

课堂状态判断没有额外训练模型，而是使用规则：

- 优点：透明、可解释、便于答辩；
- 优点：不依赖额外标注数据；
- 优点：符合大作业“简单课堂状态判断”的要求；
- 缺点：复杂课堂场景下不如学习型模型灵活。

### 13.2 为什么视频按秒采样

逐帧分析会导致计算量大，特别是每帧都要检测人脸和跑 CNN。课堂状态变化通常不需要毫秒级判断，所以默认 1 秒 1 帧：

- 能体现趋势；
- 速度更稳定；
- 符合说明书“按 1 秒 1 帧抽取”的延展任务。

### 13.3 为什么不做人脸身份跟踪

当前视频统计的是“人脸实例”，不是“唯一学生身份”。也就是说，同一个学生在不同采样帧会被多次统计。

这样设计的原因：

1. 大作业重点是检测、识别、统计和状态分析；
2. 身份跟踪会显著增加复杂度；
3. 时序趋势关注的是每个时间点的整体状态，而不是追踪每个学生；
4. 在有限课程项目中，这个取舍更稳定。

后续可扩展方向：

- 增加人脸跟踪；
- 使用 DeepSORT 或光流跟踪；
- 做学生级别的长期情绪变化分析。

### 13.4 为什么保留 WebRTC 但不推荐主演示

WebRTC 是浏览器实时视频流方案，但它依赖：

- 浏览器摄像头权限；
- localhost 或 HTTPS；
- 网络协商；
- STUN/TURN；
- 浏览器与 Python 后端连接稳定性。

实际测试中可能出现连接等待。因此项目保留 WebRTC 作为实验性功能，同时增加 OpenCV 本地实时模式作为主演示方案。

## 十四、现场讲解建议

如果助教问“你的系统怎么实现的”，可以按这个顺序讲：

1. **输入层**：图片、视频、摄像头都由 `app.py` 接收。
2. **统一单帧处理**：所有输入最终变成一帧图像，交给 `pipeline.py`。
3. **人脸检测**：`face_detector.py` 用 MediaPipe + Haar 找所有人脸。
4. **表情识别**：`expression_recognizer.py` 裁剪人脸并用 CNN3 输出 7 类表情。
5. **统计判断**：`analyzer.py` 统计表情比例并判断课堂状态。
6. **视频时序**：`temporal_analyzer.py` 对视频逐帧采样，生成趋势图和三级预警。
7. **展示导出**：`utils.py` 和 `app.py` 完成画框、图表、CSV、图片和时序日志。

一句话总结：

> 系统采用模块化流水线设计，图片、视频和摄像头都复用同一个单帧分析管线；视频在此基础上增加时序分析、预警和性能统计。

## 十五、可扩展方向

如果后续继续优化，可以考虑：

1. 使用更强的人脸检测模型，例如 RetinaFace 或 YOLO-face；
2. 使用更强的表情识别模型，例如 ResNet、EfficientNet；
3. 加入人脸跟踪，区分同一个学生跨帧出现；
4. 增加自定义课堂状态规则界面；
5. 增加批量图片分析；
6. 增加更完整的实验评估表，包括准确率、召回率和耗时对比；
7. 将 Streamlit 项目打包为桌面应用或部署到局域网服务器。
